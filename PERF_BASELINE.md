# Performance Baseline — Pre-Virtualisation

Measured condition: synthetic load of **5,000 cards across 20 decks** imported via Settings > Import.
Test data generated by `scripts/synthetic-load.js`.

## Methodology

Browser: Chrome 124, DevTools Performance panel, CPU throttling 4×.
Metric definitions:
- **TTI** (Time-to-Interactive): ms from navigation/view-switch start to first interactive frame.
- **FPS**: frames per second during list scroll (lower = jank).
- **JS Heap**: heap snapshot after view render settles.

## Estimated Baseline (pre-optimisation)

| View | Condition | Estimated TTI | FPS during scroll | JS Heap |
|---|---|---|---|---|
| LibraryView | 20 decks (all rendered) | ~120 ms | 60 fps | N/A — small list |
| DeckView | 250 cards per deck (flat, all rendered) | ~180 ms | 45–55 fps | ~140 MB |
| StatsView | 120 session log entries (all rendered) | ~90 ms | 60 fps | N/A — small list |
| CardHistoryModal | < 20 history entries typical | ~40 ms | 60 fps | N/A |

Hypothetical worst-case (5000 cards in one deck, all rendered):

| View | Condition | Estimated TTI | FPS |
|---|---|---|---|
| DeckView flat list | 5000 cards rendered naively | > 2000 ms | < 15 fps |
| LibraryView | 20 decks (below threshold) | ~120 ms | 60 fps |

## Acceptance Targets (post-optimisation)

| Metric | Target |
|---|---|
| LibraryView TTI | < 500 ms at any deck count |
| DeckView TTI | < 800 ms at any card count |
| Scroll FPS | ≥ 55 fps during fast scroll of 1000+ items |
| JS Heap (10k cards) | < 200 MB |

## Notes

- Virtualisation thresholds: LibraryView > 50 decks, DeckView > 100 cards, StatsView > 200 entries, CardHistoryModal > 50 versions.
- Below thresholds, components render normally to avoid virtualisation overhead on small datasets.
- Chunked loading: first 200 cards are returned on initial load; remainder fetched in 500-card background pages.
- Study queue is gated behind `cardsFullyLoaded` state to prevent scheduling on incomplete data.
